# 空心杯四轴无人机遥控器系统

## 项目概述

本项目是一个基于 STM32F103C8T6 + FreeRTOS 的四轴空心杯无人机**遥控器（发射端）**系统。遥控器采集摇杆和按键输入，通过 2.4GHz 无线射频模块（SI24R1/nRF24L01+）将控制数据实时发送至无人机飞控端，实现对四轴飞行器的油门、偏航、俯仰、横滚四通道控制，以及定高、关机的指令下发。

| 项目信息 | 详情 |
|---------|------|
| 主控芯片 | STM32F103C8T6 (Cortex-M3, 72MHz) |
| 实时系统 | FreeRTOS V202212.01 |
| 开发环境 | STM32CubeMX + Keil MDK-ARM v5.32 |
| 编译工具 | ARMCC v5.06 |
| 无线方案 | SI24R1 (nRF24L01+ 兼容) @ 2.4GHz, 2Mbps |
| 显示方案 | 128×64 OLED (SPI 模拟) |
| 电源管理 | IP5305T 电池管理 IC |
| 输入设备 | 四轴摇杆 (ADC×4) + 6 按键 (GPIO) |

## 软件设计

### 任务调度

| 任务名 | 周期 | 栈大小 | 优先级 | 功能 |
|--------|------|--------|--------|------|
| **vCommTask** | 6ms (166Hz) | 256 words | 4 | 数据组帧并通过 SI24R1 发送 |
| **vJoystickTask** | 6ms (166Hz) | 128 words | 4 | 摇杆 ADC 采样、归一化、校准 |
| **vKeyTask** | 10ms (100Hz) | 128 words | 4 | 按键扫描、消抖、动作分发 |
| **display_task** | 10ms (100Hz) | 128 words | 4 | OLED 仪表盘刷新 |
| **vPowerTask** | 10s | 128 words | 4 | IP5305T 电源 IC 周期性脉冲 |

各任务间通过全局 `Remote_Struct` 结构体共享数据，使用 `taskENTER_CRITICAL()` / `taskEXIT_CRITICAL()` 保护临界区。

### 数据流

```
摇杆(ADC) ──→ DMA 循环缓冲 ──→ vJoystickTask
                                    │
                              ADC→0~1000 归一化
                              − Joystick_bias 校准
                              − LIMIT 限幅
                                    │
                                    ▼
按键(GPIO) ──→ vKeyTask ──→ Remote_Struct (全局共享)
                                    │
                                    ▼
                              vCommTask
                                    │
                              组帧 (17字节):
                              ┌─────┬────────┬──────┬────────┐
                              │帧头3 │数据8   │标志2 │校验和4 │
                              │"WQM"│THR YAW │PWD   │SUM32   │
                              │     │PIT ROL │FIX   │        │
                              └─────┴────────┴──────┴────────┘
                                    │
                                    ▼
                              SI24R1 TX @ 2.4GHz
```

### 通信协议设计

**帧格式 (17 字节):**

| 偏移 | 长度 | 字段 | 说明 |
|------|------|------|------|
| 0 | 3 | 帧头 `"WQM"` (0x57 0x51 0x4D) | 帧同步标识 |
| 3 | 2 | THR (大端 int16) | 油门值 0~1000 |
| 5 | 2 | YAW (大端 int16) | 偏航值 0~1000 |
| 7 | 2 | PIT (大端 int16) | 俯仰值 0~1000 |
| 9 | 2 | ROL (大端 int16) | 横滚值 0~1000 |
| 11 | 1 | power_down | 关机标志 (边沿触发) |
| 12 | 1 | fix_height | 定高标志 (边沿触发) |
| 13 | 4 | Checksum (大端 uint32) | 前 13 字节累加和 |

**设计要点：**
- 帧头 `"WQM"` 用于飞控端帧同步，避免数据错位
- `power_down` 和 `fix_height` 采用**边沿触发**：发送后立即清零，确保飞控端只响应一次
- 32 位累加和校验保证数据完整性
- 大端字节序便于飞控端直接解析

### SI24R1 无线配置

| 参数 | 值 | 说明 |
|------|-----|------|
| 工作频率 | 2476MHz (CH76) | 2.4GHz ISM 频段 |
| 空中速率 | 2 Mbps | 最高速率，减小延迟 |
| 发射功率 | +7 dBm | 最大功率 |
| 地址宽度 | 5 字节 | `{0x0A, 0x01, 0x07, 0x0E, 0x01}` |
| CRC | 16 位 | 硬件 CRC 校验 |
| 自动重传 | 10 次, 250μs+86μs 间隔 | Enhanced ShockBurst |
| 有效载荷 | 17 字节 | 与帧长度匹配 |

### 摇杆数据处理

**归一化公式:**
```c
remote_data->THR = 1000 - remote_data->THR * 1000 / 4095;
```
- ADC 12 位原始值 (0~4095) → 归一化值 (0~1000)
- 取反 (`1000 - ...`)：匹配物理摇杆方向和逻辑控制方向

**自动校准:**
长按 RIGHT_X 键触发，采样 100 次求平均值，计算各通道偏移量 `Joystick_bias[]`，之后所有采样值减去偏移量，补偿机械回中误差。

**微调:**
方向键上下左右每次调整对应通道偏置 ±10，实现飞行中的精细微调。

### 按键处理

| 按键 | 功能 |
|------|------|
| UP/DOWN | PIT(俯仰) 微调 ±10 |
| LEFT/RIGHT | ROL(横滚) 微调 ±10 |
| LEFT_X 短按 | 发送关机信号 (power_down=1) |
| RIGHT_X 短按 | 发送定高切换信号 (fix_height=1) |
| RIGHT_X 长按 (>500ms) | 触发摇杆自动校准 |

消抖策略：10ms 延时后重新读取确认；长按通过 `xTaskGetTickCount()` 计时，超过 500ms 判定为长按。

## 模拟开发历程

### 第一阶段：需求分析与方案选型（第 1-2 周）

接到任务：为一款空心杯四轴无人机开发遥控器。核心需求：
- 四通道摇杆控制（油门/偏航/俯仰/横滚）
- 2.4GHz 无线通信，传输距离 ≥ 50m
- OLED 屏幕实时显示通道数据
- 电池供电，需电源管理
- 支持定高、关机等辅助功能

**选型决策：**
- **主控**：STM32F103C8T6。Cortex-M3 内核 72MHz，外设丰富，生态成熟，成本低。对比过 STM32F4 系列，考虑到控制任务计算量不大、20KB RAM 用 FreeRTOS 足够，103 是性价比最优解。
- **RTOS**：FreeRTOS。相比裸机循环，RTOS 能将不同频率的任务解耦（摇杆 166Hz / 按键 100Hz / 显示 100Hz / 电源 0.1Hz），代码结构更清晰，且 FreeRTOS 在 STM32 生态中支持最好（CMSIS-RTOS 兼容）。
- **无线方案**：nRF24L01+（实际使用国产兼容芯片 SI24R1）。对比过蓝牙（延迟高、距离短）和 Wi-Fi（功耗高、协议栈重），2.4GHz 私有协议在延迟（2Mbps 空中速率）和距离上最适合无人机遥控场景。
- **显示**：128×64 OLED (SSD1306 兼容)。对比过 TFT 彩屏，OLED 在阳光下可读性好、功耗低、驱动简单。

### 第二阶段：硬件搭建与 CubeMX 配置（第 2-3 周）

使用 STM32CubeMX 进行引脚分配和外设初始化配置。这一阶段的踩坑与收获：

- **SPI 与模拟 SPI 的取舍**：SI24R1 使用硬件 SPI1（9Mbps），因为 2Mbps 空中速率下，SPI 通信不能成为瓶颈。OLED 则使用 GPIO 模拟 SPI，因为屏幕刷新率要求低（100Hz），且引脚更灵活。
- **DMA 循环模式**：ADC 采集四通道摇杆，配置 DMA1 Channel1 循环模式，CPU 零干预自动更新 `adc_buff[4]`，释放 CPU 给 RTOS 任务调度。
- **时钟树验证**：HSE 8MHz → PLL×9 → 72MHz，特别确认了 ADC 时钟 = APB2/6 = 12MHz（STM32F1 ADC 最大 14MHz 限制）。

### 第三阶段：驱动层开发（第 3-5 周）

自底向上逐层开发：

1. **SI24R1 驱动**（最核心、最耗时）：
   - 实现了完整的 SPI 寄存器读写封装
   - 关键问题：SPI 在 RTOS 多任务环境下被抢占导致数据错乱 → 解决方案：在 SPI 读写函数中加 `taskENTER_CRITICAL()` / `taskEXIT_CRITICAL()` 临界区保护
   - 上电自检机制：写入 TX_ADDR 后立即读回比较，确保 SPI 通信和模块都正常工作，否则阻塞启动并打印错误信息
   - 发送流程：写 TX FIFO → 拉高 CE → 轮询 STATUS 寄存器等待 TX_DS 或 MAX_RT → 清除中断标志
   - Enhanced ShockBurst 自动应答模式：发送后等待 ACK，超时自动重传（最多 10 次），大大简化了应用层逻辑

2. **OLED 驱动**：
   - GPIO 模拟 SPI 时序驱动 SSD1306 兼容屏
   - 编写了 ASCII 6×12、8×16 字体和中文 16×16 字库
   - 自定义进度条绘制函数，用于显示各通道值

3. **摇杆驱动**：
   - DMA 循环缓冲读取 4 通道 ADC
   - 12 位 ADC 精度 → 0~1000 归一化映射

4. **按键驱动**：
   - 两级消抖：10ms 延时 + 重新确认
   - 长按检测：基于 FreeRTOS tick 计时，500ms 阈值

5. **IP5305T 电源管理**：
   - 周期性 GPIO 脉冲维持电源 IC 工作状态

### 第四阶段：应用层与 RTOS 集成（第 5-6 周）

1. **FreeRTOS 任务划分**：
   - 按照"不同频率 = 不同任务"原则拆分
   - 摇杆和通信都定在 6ms 周期（166Hz），保证控制实时性
   - 使用 `vTaskDelayUntil()` 而非 `vTaskDelay()`，保证严格周期调度

2. **通信协议设计**：
   - 帧头 `"WQM"` 用于接收端帧同步
   - `power_down` / `fix_height` 边沿触发：发送后清零，避免飞控端重复执行
   - 32 位累加和校验，平衡了计算开销和检错能力

3. **摇杆校准算法**：
   - 100 次采样求平均得各通道偏置
   - THR 通道以 0 为基准（油门最低位），其他三通道以 500 为基准（摇杆中位）
   - 微调功能：方向键 ±10 步进调整偏置

4. **OLED 仪表盘**：
   - 中文显示通道名
   - 进度条可视化各通道实时值（以中位 500 为界分左右两段）

### 第五阶段：联调与优化（第 6-8 周）

1. **SI24R1 通信稳定性**：
   - 初期偶尔丢包 → 开启 Enhanced ShockBurst 自动重传（10 次），问题解决
   - 多套设备同时工作时的频道冲突 → 预留频道切换功能（通过 `RF_CH` 寄存器）

2. **FreeRTOS 栈溢出排查**：
   - 使用 `uxTaskGetStackHighWaterMark()` 监控各任务剩余栈空间
   - vCommTask 初始分配 128 words，帧缓冲区较大导致接近溢出 → 增加到 256 words

3. **按键误触问题**：
   - 摇杆操作时偶尔误触辅助键 → 增加 10ms 消抖 + 长按 500ms 双重判定

4. **系统实时性验证**：
   - 用逻辑分析仪实测 SPI 通信时序，确认 6ms 周期内能完成一次完整的采样-组帧-发送流程
   - `taskENTER_CRITICAL()` 临界区最长持续时间约 20μs，不影响系统实时性

## 技术难点与解决方案

### 1. 多任务环境下的 SPI 竞争

**问题**：vCommTask 使用 SPI1 与 SI24R1 通信，如果在 SPI 传输中途被 RTOS 调度打断（虽然同优先级时间片轮转不会抢占，但中断可能触发优先级更高的任务就绪），可能导致数据错乱。

**解决**：在 SPI 读写函数的单字节传输前后加临界区保护：
```c
static uint8_t SPI_RW(uint8_t byte) {
    uint8_t result;
    taskENTER_CRITICAL();   // 禁止任务切换
    HAL_SPI_TransmitReceive(&hspi1, &byte, &result, 1, 1000);
    taskEXIT_CRITICAL();    // 恢复任务切换
    return result;
}
```

### 2. 边沿触发信号的设计

**问题**：`power_down` 和 `fix_height` 如果持续为 1，飞控端会反复执行关机/定高切换动作。

**解决**：在发送后立即清零，保证每按一次键飞控端只响应一次。这个简单的"边沿触发"设计避免了复杂的握手机制。

### 3. 摇杆机械误差补偿

**问题**：低成本摇杆电位器中位电压存在个体差异，且随温度漂移。

**解决**：设计了两级补偿：
- **粗校**：长按 RIGHT_X 键触发 100 次采样自动校准
- **细调**：飞行中通过方向键 ±10 微调

### 4. 帧同步与数据完整性

**问题**：无线通信中，如果接收端从数据中间开始解析，所有后续帧都会错位。

**解决**：
- 3 字节固定帧头 `"WQM"`：接收端在字节流中搜索该模式实现帧同步
- 32 位累加和校验：检测传输错误
- 固定帧长 17 字节：接收端知道每帧边界

## 面试常见问题与参考答案

### 基础问题

**Q1: 为什么选择 FreeRTOS 而不是裸机开发？**

> 遥控器有多个不同频率的并发任务：摇杆采样 166Hz、按键扫描 100Hz、OLED 刷新 100Hz、电源管理 0.1Hz。裸机需要用定时器中断 + 状态机在 main 循环中调度，代码耦合度高。FreeRTOS 将每个任务独立封装，使用 `vTaskDelayUntil()` 保证严格周期，代码可读性和可维护性明显优于裸机方案。此外，FreeRTOS 提供了临界区、信号量等同步机制，这在多任务共享 `Remote_Struct` 时很关键。

**Q2: 为什么 SPI 通信要加临界区保护？**

> STM32F1 的 SPI 外设不是多 Master 设计，如果 SPI 传输中途被抢占，再次恢复时 SPI 数据寄存器的状态已不可预期，可能导致数据错乱或丢失。临界区（`taskENTER_CRITICAL()`）本质是关闭全局中断并禁止任务切换，保证单字节 SPI 传输的原子性。实测临界区持续约 20μs，而最短任务周期 6ms，对实时性无影响。

**Q3: DMA 循环模式的好处是什么？**

> ADC 采集 4 个摇杆通道，如果不用 DMA，需要 CPU 在每次 ADC 转换完成后在中断中读取数据。DMA 循环模式让硬件自动将 4 个通道的转换结果搬运到 `adc_buff[4]`，CPU 零开销。vJoystickTask 只需要在任何时刻直接读取缓冲区即可获得最新值，将 CPU 释放给通信和显示任务。

**Q4: 通信协议为什么选固定帧长而不是变长？**

> 固定帧长（17 字节）让接收端的解析逻辑非常简单：每收到 17 字节就是一帧，配合帧头和校验和即可完成帧同步。变长协议（如带长度字段）虽然灵活性更高，但对于遥控器这种固定数据结构的场景，增加了解析复杂度却没有实际收益。SI24R1 的 Enhanced ShockBurst 模式下，包长也是固定的（TX_PLOAD_WIDTH），硬件层面也适合固定帧长。

### 进阶问题

**Q5: 如果有两个遥控器同时工作，如何避免干扰？**

> 有两种方案：
> 1. **频道切换**：SI24R1 支持 126 个频道（2400MHz + CH），只需修改 `RF_CH` 寄存器即可切换频道。可以在 OLED 界面上提供频道选择功能，用户手动设置为不同频道。
> 2. **地址隔离**：SI24R1 支持 5 字节地址，不同遥控器/飞控对使用不同地址即可在同一频道上共存（逻辑通道隔离）。
> 当前项目已预留频道参数宏 `CHANNEL`，切换到频道选择功能只需增加 UI 交互和寄存器写入逻辑。

**Q6: 如何保证 166Hz 的控制频率是稳定的？**

> 使用 `vTaskDelayUntil(&preTime, 6)` 而非 `vTaskDelay(6)`。两者的区别在于：
> - `vTaskDelay(6)`：从调用时刻起等待 6ms，如果任务执行耗时 1ms，实际周期 = 1 + 6 = 7ms，周期会抖动。
> - `vTaskDelayUntil(&preTime, 6)`：以绝对 tick 为基准，保证相邻两次唤醒的间隔严格为 6ms，不受任务执行时间影响（前提是执行时间 < 周期）。
>
> 实测 vCommTask 执行时间约 1.5ms，远小于 6ms 周期，调用 `vTaskDelayUntil` 后频率稳定性 < 0.1%。

**Q7: 如果 SI24R1 发送失败（MAX_RT），你的代码怎么处理？**

> 当重传 10 次仍未收到 ACK，STATUS 寄存器的 MAX_RT 位置位。当前代码的处理是：
> ```c
> if (state & MAX_RT) {
>     Int_SI24R1_WriteByte(FLUSH_TX, 0xff);  // 清空 TX FIFO
>     return 1;  // 返回失败
> }
> ```
> 清空 TX FIFO 是必要的，否则旧的失败数据会阻塞后续发送。返回失败后，上层 `App_Comm_Send_Data()` 不做重试——因为下一轮 6ms 后会发送最新数据，飞控端的控制策略（如失控保护）会在连续丢包后接管。对于遥控场景，发送最新数据比无限重传旧数据更合理。

**Q8: 栈溢出你是怎么排查的？**

> FreeRTOS 提供 `uxTaskGetStackHighWaterMark()` 函数，返回任务历史最小剩余栈空间（以 word 为单位）。我在开发阶段在每个任务的初始化末尾打印各任务的剩余栈：
> ```c
> printf("CommTask stack: %d\n", (int)uxTaskGetStackHighWaterMark(comm_task_handle));
> ```
> 发现 vCommTask 在 128 words 下接近栈溢出（剩余不到 10 words），因为 17 字节 `data_buf` 和函数调用嵌套占用较多栈。解决方案是扩大到 256 words，同时将大缓冲区 `data_buf` 从栈上改为全局静态变量，减少栈压力。

**Q9: DMA 循环模式下，读取数据时会不会读到"一半新一半旧"的数据？**

> 这个问题问得很好。在 DMA 循环模式下，DMA 在后台持续更新 `adc_buff[4]`，如果没有同步机制，确实可能读到不一致的数据。但本项目中没有做额外同步，原因是：
> 1. 四个通道的值由 DMA 在一次 ADC 扫描完成中断后**批量**更新（ADC 扫描模式 + DMA 循环缓冲）
> 2. STM32F1 的 DMA 在搬运数据时，Cortex-M3 内核通过总线矩阵访问 SRAM 是原子的（字对齐访问）
> 3. 每个通道值独立使用，四个值之间没有跨通道的一致性要求
>
> 如果真的需要保证四个通道的快照一致性，可以加 `taskENTER_CRITICAL()` 在读 buffer 的代码前后保护，当前代码中也确实加了临界区。

**Q10: 这个项目让你重新设计的话，你会改进什么？**

> 1. **队列替代全局变量**：当前 5 个任务通过全局 `Remote_Struct` 共享数据，存在竞争风险（虽然目前用临界区保护了）。更规范的做法是使用 FreeRTOS 队列或消息缓冲，实现任务间的数据解耦。
> 2. **双向通信**：当前是单向发射，无法获取飞控端的 RSSI（信号强度）、电池电压等遥测数据。SI24R1 支持双向通信，可以增加下行链路。
> 3. **跳频扩频**：当前固定频道 76，工业遥控器通常使用 FHSS 跳频提升抗干扰能力。SI24R1 硬件支持快速频道切换，可以实现简单的跳频协议。
> 4. **故障安全**：增加看门狗任务，如果 SI24R1 连续 N 次发送失败，通过 OLED 和蜂鸣器告警用户。
> 5. **代码规范**：统一中英文注释，消除当前混用的情况；使用 Doxygen 格式的注释提高可维护性。
